# PF2e class conversion coverage and Pathmuncher lessons

Research snapshot: 2026-10-27. This is a test and implementation inventory for **WG v4 → Foundry PF2e**. Pathmuncher imports **Pathbuilder → Foundry**, so its fixtures and fixes suggest failure modes; they do not establish that Wanderer's Guide exports the same fields or that this module supports a class.

## Evidence and release rule

The [current Foundry PF2e class pack](https://github.com/foundryvtt/pf2e/tree/master/packs/pf2e/classes) contains the 29 classes below. Pathmuncher has [generated Pathbuilder fixtures for every one](https://github.com/MrPrimate/pathmuncher/tree/main/tests/fixtures/pathbuilder/generated) and [expected snapshots](https://github.com/MrPrimate/pathmuncher/tree/main/tests/fixtures/snapshots/generated). Its [Foundry survey](https://github.com/MrPrimate/pathmuncher/blob/main/tests/README.md) records unmatched content, prompts, and differences, but the generated survey fails only for exceptions. Fixture presence is **not** full parity evidence. Its targeted [fixture](https://github.com/MrPrimate/pathmuncher/blob/main/tests/foundry/fixtures.test.js), [hand-built comparison](https://github.com/MrPrimate/pathmuncher/blob/main/tests/foundry/handbuilt.test.js), and [companion tests](https://github.com/MrPrimate/pathmuncher/blob/main/tests/foundry/companions.test.js) offer stronger, narrower examples.

For each row, obtain a sanitized real WG v4 export, preserve its raw selection keys and class feature IDs, capture the matching Foundry compendium rules, then test import, reload, identical re-import, changed choice, and level change. Compare resulting actor state and source-path coverage, not just item names. A row is **unverified** until that WG-specific gate passes. No row below asserts present module support.

Legend: **P0** means class mechanics can be materially wrong while a character looks populated; **P1** means shared conversion or lower-complexity class checks. Test targets are hypotheses to validate against real WG data, not assumptions about WG's schema.

## Cross-class conversion notes to implement

1. **Do not infer absent source choices.** Pathmuncher's [known limitations](https://docs.ddb.mrprimate.co.uk/docs/pathmuncher/known-limitations) and [import notes](https://docs.ddb.mrprimate.co.uk/docs/pathmuncher/import-report) distinguish missing signature/prepared selections, variant mismatches, unresolved rule choices and companion guesses. Inspect whether WG v4 supplies each answer. If absent, present an unresolved choice; preserve a user's Foundry selection on re-import when still legal.
2. **Preserve PF2e class rules and grants.** A historical [class/background reference bug](https://github.com/MrPrimate/pathmuncher/issues/6) left a Summoner looking populated but unable to gain class features on level change. Test level down/up or progression after import, and compare granted children and slot locations with a hand-built actor. Deduplicate only with an explicit owner/grant relationship.
3. **Companions are actors.** Eidolons, animal companions and constructs need stable parent links, idempotent re-import, reviewed guesses and distinct ownership of evolution/modification feats. Pathmuncher's [companion documentation](https://docs.ddb.mrprimate.co.uk/docs/pathmuncher/companions) requires an additional compendium module for its companion implementation; this module must declare its own dependency/unsupported result based on the installed world.
4. **Archetypes and variants cross class boundaries.** [Dual class is unsupported by Pathmuncher](https://docs.ddb.mrprimate.co.uk/docs/pathmuncher/known-limitations), so do not infer secondary-class support from class fixtures. Test free archetype, Summoner Dedication, Exemplar Dedication, mythic slots and variant mismatch separately. An [open mythic request](https://github.com/MrPrimate/pathmuncher/issues/51) is a test lead, not a current WG defect.
5. **Re-import must preserve manual work.** An [open Pathmuncher request](https://github.com/MrPrimate/pathmuncher/issues/47) describes existing actor actions/bonus feats being deleted. Keep module-owned item identity and review removals before applying. An [open temporary-actor permission report](https://github.com/MrPrimate/pathmuncher/issues/55) motivates testing player permissions and cleanup; avoid requiring deletion of an actor the user cannot delete.
6. **Closed issues are historical regressions.** The linked Kineticist, Inventor and Ranger issues above were closed against older module/system versions. Reproduce their *behavioral assertions* in our WG fixtures without claiming current Pathmuncher defects. Open issue status likewise does not prove a bug persists on current versions.

## Fixture and acceptance matrix

Maintain one row per real WG export with: class and level; WG revision; Foundry/PF2e versions; optional module dependencies; source IDs and full selection paths; expected class choices, spell entries/resources, granted items, feat slot/level, companion identity, derived rules; expected unresolved source paths. Prioritize one low-level and one progressed character for each P0 class; add archetype, remaster/legacy and changed-choice variants when the class exercises them. Pathmuncher JSON is useful to design scenarios, but cannot supply WG-specific golden values.

For each fixture, run pure decoder/plan assertions and a Foundry-world test of first import, reload, identical re-import, changed choice, level change and cancellation/failure recovery. Require zero unexplained dropped WG paths, no duplicate managed/granted items, legal persisted PF2e choices and a specific report for every unavailable mechanic. A class stays **experimental** until these pass on the declared Foundry/PF2e versions.


## Class rules registry design

This matrix contains 29 class rows. PR #14 adds the design for a normalized, data-driven class rules registry in [CLASS_RULE_REGISTRY.md](CLASS_RULE_REGISTRY.md). The design separates discovery/schema work from the later implementation that will remove runtime hard-codes.

The registry will record class sources, selection rules, grant/dedupe relationships, spellcasting conventions, and evidence/coverage cases. The current hard-coded behavior audit covers `scripts/selections.js`, `scripts/coverage.js`, `scripts/mapping.js`, and `scripts/importer.js`. Generic safety invariants remain executable code; class-specific heuristics become validated data.
